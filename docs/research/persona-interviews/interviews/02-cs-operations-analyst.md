## Interview 02 — 이수진: CSV 반출이 잦은 CS Operations Analyst

> 합성 페르소나 시뮬레이션이며 실제 사용자 인터뷰나 수요의 증거가 아니다.

### 페르소나

- 29세, B2B SaaS CS Operations Analyst, 경력 4년
- SQL은 SELECT와 간단한 JOIN까지 가능
- 주로 Metabase saved question과 Google Sheets 사용
- 복잡한 요청은 개발자에게 SQL 또는 CSV 추출을 부탁함
- 터미널은 배포 로그를 따라 볼 때 외에는 거의 사용하지 않음
- 빠르게 시도하는 편이지만 오류 메시지와 설정 파일에 쉽게 막힘
- “안전한 도구”보다 “팀과 같은 결과를 다시 열고 공유할 수 있는 도구”를 선호

### 인터뷰 목적

CSV 수요가 높은 비개발 데이터 실무자에게도 datavase의 가치가 전달되는지, 터미널이라는 형식이 근본적인 진입 장벽인지 확인한다.

### 인터뷰

**Interviewer:** 최근 고객 데이터가 필요했던 일을 하나만 처음부터 끝까지 설명해주세요.

**수진:** 지난주에 특정 요금제를 쓰다가 해지한 병원 목록이 필요했어요. Metabase에서 비슷한 질문을 찾았는데 날짜 조건이 달라서 복사한 뒤 수정했어요. 결과를 CSV로 내려받아 Sheets에서 담당자 컬럼을 붙였고요.

**Interviewer:** 그 과정에서 가장 어려웠던 부분은 무엇이었나요?

**수진:** 쿼리가 맞는지 확신이 없는 거요. 컬럼 이름도 비슷하고, 탈퇴일인지 구독 종료일인지 헷갈렸어요. 실행 자체나 CSV 다운로드는 어렵지 않았어요.

**Interviewer:** 직접 운영 DB에 접속한 적도 있나요?

**수진:** 없어요. 권한도 없을 것 같아요. 운영 DB를 봐야 하면 개발팀에 요청합니다.

**Interviewer:** 왜 개발팀에 요청하나요?

**수진:** 접근 방법을 모르기도 하고, 잘못 건드리면 안 되니까요. 읽기만 된다고 해도 어떤 테이블을 봐야 하는지 모르겠어요.

**Interviewer:** 터미널에서 실행하는 MySQL 클라이언트가 있고, datasource를 read-only로 설정할 수 있습니다. 결과는 표로 보이고 CSV로 저장할 수 있어요. 첫 느낌은 어떤가요?

**수진:** 저를 위한 제품 같지는 않아요. 터미널이라는 말에서 이미 개발자 도구처럼 느껴져요.

**Interviewer:** 설치가 명령어 한 줄이고 사용 화면은 마우스도 지원하는 TUI라면요?

**수진:** 그래도 DB 주소나 계정 설정을 해야 하잖아요. 회사가 설치해서 아이콘처럼 열어주는 게 아니면 혼자 하지는 않을 것 같아요.

**Interviewer:** CSV 저장 기능은 자주 쓰지 않나요?

**수진:** CSV는 많이 쓰지만 Metabase에도 있어요. CSV를 내려받기 전에 맞는 데이터를 찾는 게 더 중요해요.

**Interviewer:** read-only라서 실수로 수정할 수 없다는 점은요?

**수진:** 안심은 되는데, 그렇다고 제가 운영 DB를 직접 봐도 된다는 뜻은 아니죠. 회사 권한 정책이 먼저일 것 같아요.

**Interviewer:** 화면에서 테이블 목록과 컬럼을 볼 수 있습니다.

**수진:** 설명이 붙어 있나요? `hospital_status` 같은 이름만 보면 어떤 값을 써야 할지 모르거든요. 자주 쓰는 쿼리나 팀에서 검증한 쿼리를 골라 쓸 수 있으면 더 좋아요.

**Interviewer:** query favorites가 있다면 사용할까요?

**수진:** favorites보다 팀 템플릿에 가까워야 해요. 누가 만든 쿼리인지, 마지막으로 언제 확인됐는지 보여야 믿고 써요.

**Interviewer:** 지금 제품을 직접 설치해볼 가능성은 어느 정도인가요?

**수진:** 거의 없어요. 개발자가 제 노트북에 설치하고 datasource랑 쿼리까지 준비해준다면 한 번은 써볼 수 있지만, 그 정도면 Metabase 질문을 하나 만들어달라고 할 것 같아요.

**Interviewer:** 다음 설명 중 가장 이해하기 쉬운 것은 무엇인가요?

1. A terminal MySQL client
2. A safer MySQL client for production reads
3. Export production data without risking a write

**수진:** 3번이 무슨 일을 하는지는 제일 잘 알겠어요. 그래도 제가 production data를 직접 봐도 되는지부터 궁금해요.

**Interviewer:** 어떤 상황이면 이 제품이 필요할까요?

**수진:** Metabase가 장애 났는데 급하게 데이터를 봐야 하고, 개발자가 옆에서 접속까지 해준 상황? 그런데 평소 사용 장면은 잘 안 떠올라요.

**Interviewer:** 제품에서 하나를 바꿀 수 있다면요?

**수진:** 설치보다도 시작 화면에 제가 해야 할 작업이 보여야 해요. datasource나 table보다 ‘해지 고객 추출’ 같은 이름으로요. 하지만 그건 지금 제품과 다른 제품 같네요.

### Interview 02 결과

이 페르소나는 CSV 수요가 높음에도 채택 가능성이 매우 낮다. 핵심 문제는 export 기능 부족이 아니라 다음 세 가지다.

1. 운영 DB 접근 권한이 없다.
2. 테이블·컬럼 의미를 몰라 올바른 쿼리를 만들기 어렵다.
3. 결과의 공유·재현·검증이 로컬 터미널보다 중요하다.

read-only는 심리적 안심을 주지만 조직 권한을 대신하지 못한다. 이 사용자를 잡으려면 팀 쿼리 카탈로그, 데이터 정의, 공유 링크, 실행 이력 같은 협업 기능이 필요하고, 이는 PR #82에서 줄인 제품 범위를 다시 크게 만든다.
