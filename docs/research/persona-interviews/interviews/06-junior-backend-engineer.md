## Interview 06 — 박민준: 운영 조회가 아직 두려운 주니어 백엔드 엔지니어

> 합성 페르소나 시뮬레이션이며 실제 사용자 인터뷰나 수요의 증거가 아니다.

### 페르소나

- 26세, 백엔드 엔지니어, 경력 1년 6개월
- 개발자 약 20명의 커머스 스타트업
- Java, Spring Boot, MySQL 8
- 개발 DB에서는 IntelliJ Database Tools를 주로 사용
- 터미널은 애플리케이션 실행, 로그 확인, Git 작업 정도에만 사용
- 운영 DB 계정은 있지만 반드시 선임과 사전 협의한 뒤 접속
- SQL 문법보다 현재 접속한 서버와 실행 대상에 대한 불안이 큼
- 새로운 CLI의 단축키와 설정 파일을 외우는 데 부담을 느낌
- 실수를 피하기 위해 검증된 쿼리를 복사하고 실행 전 여러 번 확인함

### 인터뷰 목적

터미널과 운영 DB 경험이 적은 주니어 개발자에게 datavase의 작은 기능 범위가 학습 부담을 줄이는지 확인한다. 또한 session read-only가 실제 안전 불안을 완화하는지, 아니면 새로운 도구와 환경을 판단해야 하는 부담을 추가하는지 검증한다.

### 인터뷰

**Interviewer:** 최근 운영 DB에 직접 접속했던 일을 처음부터 끝까지 설명해주세요.

**민준:** 지난달에 고객 한 명의 주문 상태가 화면과 다르게 보이는 문제가 있었어요. 로그에서 주문 ID를 찾고 선임에게 말씀드렸더니 운영 replica에서 확인해보라고 하셨어요. 사내 위키에 있는 명령어를 복사해서 SSH 접속하고, 다시 mysql 접속 명령어를 복사했어요. 쿼리도 제가 새로 만들기보다 개발 DB에서 확인한 SELECT를 선임에게 보여드린 다음 실행했습니다.

**Interviewer:** 실제 데이터 확인에는 얼마나 걸렸나요?

**민준:** 조회 자체는 1분도 안 걸렸어요. 그런데 접속 전에 확인받고 명령어를 다시 보는 데 10분 넘게 걸렸던 것 같아요.

**Interviewer:** 무엇을 가장 오래 확인했나요?

**민준:** 지금 접속한 곳이 replica가 맞는지, database 이름이 맞는지, 쿼리에 UPDATE가 섞이지 않았는지 봤어요. 프롬프트만 보면 개발 DB인지 운영 DB인지 바로 구분이 안 돼서 `SELECT DATABASE()`도 다시 실행했고요.

**Interviewer:** mysql CLI의 결과 화면은 불편하지 않았나요?

**민준:** 컬럼이 많아서 조금 불편했어요. 그래도 한 row만 보는 작업이라 `\G`를 쓰라고 배워서 해결했습니다. 화면보다 잘못 실행할까 봐 긴장되는 게 더 컸어요.

**Interviewer:** 운영 DB에서 실제로 잘못된 쿼리를 실행한 적이 있나요?

**민준:** 아직은 없어요. 없어서 더 조심하는 것 같아요. 입사 초기에 다른 팀에서 운영 데이터를 잘못 수정한 사례를 들었거든요. 저는 SELECT만 쳐도 혹시 부하를 만들까 걱정됩니다.

**Interviewer:** 그 걱정 때문에 작업을 포기하거나 다른 사람에게 부탁한 적도 있나요?

**민준:** 네. 급하지 않은 건 선임에게 쿼리를 보내고 대신 결과만 받아본 적이 있어요. 제가 직접 접속하는 것보다 느리지만 책임이 덜 무섭다고 느꼈어요.

**Interviewer:** 새로운 terminal MySQL client를 도입한다면 가장 먼저 무엇을 확인하겠어요?

**민준:** 실행 방법보다 이게 어느 서버에 연결됐는지를 볼 것 같아요. 설치해놓고 datasource 이름을 잘못 고르면 더 위험할 수 있잖아요. 설정 파일도 제가 직접 수정해야 한다면 처음에는 선임에게 봐달라고 할 것 같아요.

**Interviewer:** datavase는 datasource를 이름으로 저장하고 실행할 때 선택할 수 있습니다.

**민준:** 이름만 있으면 부족할 것 같아요. `prod-read`라고 써 있어도 실제 주소가 바뀌었을 수 있으니까요. host, database, user가 화면에 계속 보였으면 좋겠어요.

**Interviewer:** datasource에 `read_only: true`를 설정하면 connection을 session-level read-only로 만듭니다. UPDATE나 DELETE 같은 일반적인 write는 서버에서 거부됩니다.

**민준:** 그건 안심돼요. 제가 SQL을 잘못 붙여넣는 실수는 줄여줄 것 같아요. 그런데 설정이 실제로 적용됐는지는 어떻게 알아요?

**Interviewer:** 화면에 read-only 상태를 표시할 수 있습니다.

**민준:** 설정 파일에 true라고 적혀 있다는 표시인지, 지금 연결된 DB가 확인해준 상태인지 궁금해요. 저는 그 차이를 직접 판단하기 어려워서 초록색으로 보이면 그냥 믿을 것 같거든요.

**Interviewer:** read-only datasource에서는 이제 혼자 운영 데이터를 확인할 수 있을까요?

**민준:** 바로 그렇지는 않을 것 같아요. read-only여도 느린 SELECT는 실행할 수 있고, 개인정보를 조회하는 문제도 있잖아요. 회사에서 이 도구와 datasource 설정을 검토하고 사용해도 된다고 정해줘야 혼자 쓸 수 있을 것 같아요.

**Interviewer:** 설치가 Homebrew 명령어 한 줄이라면 직접 설치하겠어요?

**민준:** 설치는 할 수 있어요. 그런데 설치가 쉽다는 것과 업무에서 써도 된다는 건 다른 것 같아요. 공식적으로 팀에서 쓰는 도구가 아니면 장애 상황에서 처음 꺼내지는 않을 것 같아요.

**Interviewer:** 테이블 목록, SQL editor, result grid, CSV 저장 네 가지 작업만 제공해서 학습할 기능은 많지 않습니다.

**민준:** 기능이 적은 건 좋아요. 하지만 단축키를 새로 외워야 하면 부담돼요. 제가 자주 안 쓰면 다음에 접속했을 때 다 잊어버릴 것 같아요.

**Interviewer:** 실행은 `F5`, 복사는 여러 조합의 단축키를 사용합니다.

**민준:** `F5`는 익숙해서 괜찮아요. cell, row, 전체 결과마다 다른 키가 있으면 처음에는 메뉴를 찾아볼 것 같아요. 화면 아래에 지금 할 수 있는 동작이 보이면 좋겠어요.

**Interviewer:** 마우스로 메뉴를 선택할 수도 있습니다.

**민준:** 그러면 시작은 할 수 있을 것 같아요. 다만 터미널 프로그램인데 마우스가 된다는 사실을 설명에서 먼저 알기는 어려울 것 같아요.

**Interviewer:** autocomplete가 있다면 SQL 작성이 더 안전해질까요?

**민준:** 오타는 줄겠지만 쿼리가 맞다는 확신까지 주지는 않을 것 같아요. 존재하는 컬럼을 골랐다고 업무 의미가 맞는 건 아니니까요. 오히려 자동완성을 믿고 운영에서 바로 실행할까 봐 조심해야 할 것 같아요.

**Interviewer:** 실행 전 SQL이 SELECT인지 확인하고, write 문이면 경고하는 기능은 어떨까요?

**민준:** 도움이 되지만 경고가 자주 나오면 그냥 Enter를 누르게 될 것 같아요. production read-only datasource에서는 애초에 write가 실패하고, 화면에서 그 상태를 확실히 보여주는 편이 더 믿음이 가요.

**Interviewer:** 다음 중 어떤 설명이 가장 이해하기 쉽나요?

1. A terminal MySQL/MariaDB client
2. A better MySQL client for humans
3. A safer MySQL client for production reads
4. Replace `ssh → mysql` with `ssh → dv`

**민준:** 3번이 제가 왜 써야 하는지 가장 잘 보여줘요. 4번은 기존에 mysql을 자주 쓰는 사람에게는 이해가 빠르겠지만, 저는 `dv`를 새로 배워야 한다는 생각부터 들어요.

**Interviewer:** 20초짜리 demo에서 datasource 선택, SELECT 실행, CSV 저장, UPDATE 거부를 보여준다면 설치해볼 마음이 생기나요?

**민준:** 혼자 설치하기보다 선임에게 링크를 보내볼 것 같아요. “우리도 production 조회용으로 이거 써도 되나요?”라고 물어볼 것 같습니다.

**Interviewer:** 선임이 허용한다면 mysql CLI 대신 사용할까요?

**민준:** 접속 정보가 미리 설정되어 있고 화면에서 환경을 분명히 구분할 수 있다면요. 처음 두세 번은 mysql과 같이 확인해볼 것 같고, 결과가 정확하고 접속이 매번 잘되면 그다음부터 사용할 수 있을 것 같아요.

**Interviewer:** 한 번 사용한 뒤 다시 mysql로 돌아가게 되는 상황은 무엇인가요?

**민준:** 실행했는데 아무 반응이 없거나, 접속이 끊겼는데 화면에서 알기 어렵거나, read-only 표시를 믿었는데 write가 실행되는 경우요. 단축키를 잊은 건 다시 찾아보면 되지만 안전 상태를 믿을 수 없으면 안 쓸 것 같아요.

**Interviewer:** 기능을 하나 추가할 수 있다면 무엇을 원하나요?

**민준:** 새 기능보다 환경을 더 확실히 보여줬으면 해요. production은 색이나 경고 문구가 다르고, 현재 host와 database가 항상 보이는 식으로요. 가능하면 팀에서 검토한 datasource 설정을 그대로 받아서 쓰고 싶어요.

**Interviewer:** 개인 설정 파일을 Git으로 공유하면 될까요?

**민준:** 비밀번호가 빠져 있고 회사에서 관리 방법을 정해준다면 가능할 것 같아요. 하지만 파일을 복사한 뒤 각자 수정해야 하면 잘못된 값이 생길까 걱정돼요. 처음 연결할 때 실제 대상 정보를 다시 확인해주는 과정이 있으면 좋겠어요.

**Interviewer:** 지금 상태에서 직접 채택할 가능성은 어느 정도인가요?

**민준:** 제가 결정해서 쓰지는 않을 것 같아요. 선임이 설정을 검토하고 팀에서 production 조회 도구로 정해준다면 사용할 가능성은 높아요. 저는 사용자일 수는 있지만 도입 결정자는 아닌 것 같습니다.

### 결정적 발언

> “조회는 1분도 안 걸렸는데, 제가 맞는 곳에서 맞는 쿼리를 실행하는지 확인하는 데 10분 넘게 걸렸어요.”

> “저는 초록색으로 보이면 그냥 믿을 것 같아서, 설정값인지 서버가 확인한 상태인지 구분돼야 해요.”

> “설치가 쉽다는 것과 업무에서 써도 된다는 건 다른 것 같아요.”

> “저는 사용자일 수는 있지만 도입 결정자는 아닌 것 같습니다.”

### Interview 06 결과

주니어 백엔드 엔지니어에게 mysql CLI의 결과 가독성은 부차적인 문제였다. 더 큰 비용은 현재 환경, 실행 SQL, 조직 허용 범위를 스스로 판단해야 하는 데서 발생했다. datavase의 작은 기능 범위는 학습 부담을 낮추지만, 새로운 datasource와 안전 표시를 신뢰하는 방법까지 학습해야 하므로 도구 자체만으로 불안을 제거하지는 못한다.

session read-only는 우발적인 write에 대한 걱정을 분명히 줄인다. 그러나 이 페르소나는 이를 느린 SELECT, 개인정보 접근, 잘못된 서버 선택까지 해결하는 포괄적 안전 장치로 오해할 가능성이 있다. 따라서 `read_only: true`를 강하게 홍보할수록 실제 session 상태와 보장하지 않는 범위를 함께 보여줘야 한다.

이 페르소나는 잠재적인 실제 사용자지만 구매자나 독립적인 도입자는 아니다. 채택 경로는 개인 개발자의 발견보다 선임 또는 Platform 팀의 검토와 표준 datasource 배포에 가깝다.

| 관찰 | 제품에 주는 의미 |
|---|---|
| 조회보다 실행 전 확인에 시간이 더 많이 듦 | grid보다 environment clarity가 우선 |
| 새 CLI 단축키를 기억하기 어려움 | 화면 내 동작 안내와 메뉴가 필요 |
| read-only 상태를 그대로 신뢰할 가능성이 높음 | config 값과 실제 session 확인 상태를 구분해야 함 |
| 운영 접근 정책을 스스로 판단하지 않음 | 팀 승인과 onboarding 경로가 채택에 중요 |
| autocomplete를 안전 보장으로 보지 않음 | 편의 기능을 safety claim과 분리해야 함 |
| 장애 상황에서 익숙한 도구로 회귀함 | 반복 사용 전 reliability 검증이 필요 |

### 실제 사용자 인터뷰 검증 후보

1. 경력 0~3년 백엔드 엔지니어가 최근 운영 DB 조회에서 실행 전 확인에 사용한 시간과 절차
2. production, staging, development 환경을 구분하기 위해 현재 사용하는 시각적·절차적 장치
3. session read-only 표시를 config 의도와 서버 확인 상태 중 무엇으로 이해하는지
4. read-only가 느린 SELECT, 개인정보 접근, DB 권한까지 보호한다고 오해하는지
5. 처음 보는 TUI에서 도움말 없이 SQL 실행, 결과 복사, 종료를 수행할 수 있는지
6. 첫 사용 이후 단축키를 잊었을 때 다시 학습하는지 mysql 또는 GUI로 돌아가는지
7. 신규 도구의 도입 결정자가 개인 개발자, 선임, Platform 팀 중 누구인지
8. 팀이 검토한 datasource 설정을 배포할 때 필요한 secret 관리와 환경 검증 절차
9. 실제 host, database, user의 상시 표시가 환경 오접속 불안을 줄이는지
10. 선임 승인과 두세 번의 병행 사용 이후 mysql CLI를 반복적으로 대체하는지
