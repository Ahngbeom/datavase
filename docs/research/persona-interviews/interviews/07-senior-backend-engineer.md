## Interview 07 — 박재민: 도구 선택권은 있지만 전환 기준이 높은 시니어 백엔드 엔지니어

> 합성 페르소나 시뮬레이션이며 실제 사용자 인터뷰나 수요의 증거가 아니다.

### 페르소나

- 38세, 시니어 백엔드 엔지니어, 경력 13년
- 개발자 약 60명의 커머스 SaaS 회사
- Java, Spring Boot, Go, MySQL 8
- 개발 환경에서는 IntelliJ와 DataGrip을 사용
- 운영 장애 대응에서는 `kubectl`, `stern`, `mysql`, 자체 운영 스크립트를 조합
- 터미널 도구 설치와 개인 workflow 변경을 스스로 결정할 수 있음
- 팀 공통 도구 도입을 제안할 영향력은 있지만 공식 표준화와 유지보수 책임은 피하려 함
- 새 도구의 기능 수보다 기존 명령과의 호환성, 실패 시 복구 가능성, 장기 유지 가능성을 중시
- 운영 DB 계정은 대부분 DB 권한 수준에서 SELECT만 허용됨

### 인터뷰 목적

도구 선택 자율성이 높은 숙련 개발자가 datavase를 시험하고 기존 `mysql` workflow에서 전환하는 조건을 확인한다. 설치 권한이나 SQL 숙련도가 문제가 아닐 때도 read-only, TUI 결과 표시, datasource 관리가 충분한 채택 이유가 되는지 검증한다.

### 인터뷰

**Interviewer:** 최근 운영 DB에 직접 접속했던 일을 하나만 처음부터 끝까지 설명해주세요.

**재민:** 이틀 전에 주문 상태가 결제 시스템과 다르다는 알림이 있었어요. 로그에서 주문 번호를 찾고 Kubernetes pod에서 애플리케이션 로그를 확인한 다음, 로컬 터미널에서 SSH tunnel 스크립트를 실행했어요. 그 상태로 `mysql`에 접속해서 주문, 결제, 이벤트 테이블을 차례로 조회했습니다.

결과를 오래 볼 필요는 없어서 `\G`로 몇 개 확인했고, 주문 번호와 상태만 팀 채널에 붙여 넣었어요. 원인은 DB가 아니라 이벤트 소비 지연이었습니다.

**Interviewer:** 그 과정에서 가장 불편했던 부분은 무엇이었나요?

**재민:** 특별히 심하게 불편하지는 않았어요. tunnel 스크립트도 있고 shell history에 쿼리도 남아 있으니까요.

굳이 꼽으면 어느 환경에 연결됐는지 계속 확인하는 일이요. 운영 계정 이름과 prompt 색을 다르게 해뒀지만, tunnel을 여러 개 열어놓으면 포트를 잘못 선택할 가능성은 있어요.

**Interviewer:** 결과가 넓어서 읽기 어렵지는 않았나요?

**재민:** `SELECT *`를 잘 안 합니다. 필요한 컬럼만 지정하고 row 하나를 볼 때는 `\G`를 써요. 결과가 크면 파일로 내보내거나 DataGrip으로 다시 봅니다. mysql 출력이 예쁘지는 않지만 업무가 막힐 정도는 아니에요.

**Interviewer:** 왜 처음부터 DataGrip을 사용하지 않았나요?

**재민:** 장애 대응 중에는 이미 터미널에 로그, pod, tunnel이 열려 있어요. 주문 하나 확인하려고 애플리케이션을 하나 더 열고 connection이 살아 있는지 기다리는 게 더 느립니다.

여러 테이블을 탐색하거나 쿼리를 오래 작성해야 한다면 DataGrip으로 옮기고요. 둘 중 하나를 완전히 대체할 생각은 없습니다.

**Interviewer:** 현재 방식에서 실수로 데이터를 변경할까 걱정한 적이 있나요?

**재민:** 예전 회사에서는 있었어요. 개발 DB라고 생각하고 운영 DB에 붙은 상태에서 UPDATE를 실행한 사람이 있었거든요.

지금 회사는 운영 조회 계정 자체에 쓰기 권한이 없습니다. 그래서 개인 클라이언트의 read-only 설정보다 계정 권한을 더 믿어요. 클라이언트 설정은 해제될 수도 있고 우회될 수도 있잖아요.

**Interviewer:** 개인이 터미널 프로그램을 새로 설치하는 데 제약이 있나요?

**재민:** 거의 없어요. Homebrew나 GitHub Release에서 받아 쓰는 정도는 자유롭습니다. 다만 DB credential을 다루는 도구라면 source와 release provenance는 확인해요.

**Interviewer:** 그렇다면 새로운 MySQL 클라이언트를 발견했을 때 무엇을 보고 설치하나요?

**재민:** 기존 도구로 해결하지 못하는 반복적인 문제가 있는지 먼저 봅니다. 그다음 최근 release와 issue 대응 상태, 설치 제거가 쉬운지, config가 어디 저장되는지 확인해요.

화면이 예쁘다는 이유만으로는 설치하지 않아요. 새 도구가 늘어나면 업데이트하고 사용법을 기억해야 하는 비용이 생기니까요.

**Interviewer:** datavase는 single binary로 실행되는 터미널 MySQL/MariaDB 클라이언트입니다. datasource를 저장하고, 테이블을 확인하고, SQL을 실행해 grid로 결과를 볼 수 있습니다. 첫 느낌은 어떤가요?

**재민:** 한 번 구경할 수는 있지만 지금 설명만으로는 바꾸지 않을 것 같아요. 저는 datasource 저장은 shell script와 DataGrip에 이미 있고, SQL 실행은 mysql로 됩니다.

grid가 정말 잘 동작하면 넓은 결과를 볼 때 편할 수는 있겠네요. 하지만 그때만 별도 도구를 열지는 모르겠어요.

**Interviewer:** datasource에 `read_only: true`를 지정하면 모든 connection이 session-level read-only로 시작하고 UPDATE가 거부됩니다.

**재민:** 방어층 하나가 추가되는 건 좋죠. 하지만 그게 핵심 기능이라고 하면 조금 약해요. 운영 DB 안전은 DB 계정과 권한에서 보장해야 합니다.

오히려 쓰기 권한이 있는 공용 계정을 그대로 두고 클라이언트 read-only를 믿게 만들면 잘못된 안전감이 생길 수도 있어요.

**Interviewer:** 그렇다면 read-only 기능은 가치가 없나요?

**재민:** 아니요. 로컬이나 staging처럼 계정에 쓰기 권한이 있지만 평소에는 조회만 하는 환경에서는 유용해요. 운영에서도 실수 방지 장치로는 의미가 있고요.

다만 보안 통제라고 표현하면 안 되고, 안전벨트 정도로 설명해야 맞습니다.

**Interviewer:** 결과를 CSV로 바로 저장하고 cell, row, 전체 결과를 복사할 수 있습니다.

**재민:** 가끔 도움이 되겠지만 자주 쓰지는 않을 것 같아요. 운영 데이터 반출은 개인정보 때문에 승인된 경로를 써야 하고, 임의로 로컬 CSV를 만드는 것을 권장하지 않아요.

장애 채널에 값 몇 개 공유할 때 row 복사는 편할 수 있습니다. 다만 탭이나 줄바꿈이 예상대로 유지돼야 해요.

**Interviewer:** 지금 datavase를 설치해볼 가능성은 어느 정도인가요?

**재민:** 30% 정도요. 동료가 실제 장애 대응에서 잘 쓴다고 보여주거나, 제가 mysql 출력 때문에 다시 DataGrip을 여는 일이 반복되면 올라갈 것 같아요.

README의 demo만 보고 바로 기본 도구로 바꾸지는 않습니다.

**Interviewer:** 도구 선택권이 충분한데도 왜 가능성이 낮나요?

**재민:** 설치 권한과 전환 의지는 다른 문제니까요. 기존 workflow가 이미 80점이면 새 도구가 90점이라는 설명만으로는 부족해요.

새 도구가 실패했을 때 결국 mysql로 돌아가야 한다면 두 도구를 모두 기억하게 됩니다. 전환하려면 중요한 상황에서 계속 믿고 쓸 수 있다는 경험이 먼저 필요해요.

**Interviewer:** 시험 사용을 결정하게 만드는 최소 조건은 무엇인가요?

**재민:** 첫째는 기존 MySQL connection 정보를 쉽게 가져오는 것, 둘째는 SSH tunnel이 예상대로 동작하는 것, 셋째는 현재 연결된 환경이 화면에서 절대 헷갈리지 않는 것이에요.

설치한 다음 YAML 문서를 읽고 datasource를 처음부터 다시 입력해야 한다면 그 자리에서 그만둘 가능성이 큽니다.

**Interviewer:** 환경을 헷갈리지 않게 하려면 무엇이 필요할까요?

**재민:** prompt 한 줄보다 화면 전체에서 계속 보여야 해요. `PRODUCTION`, hostname, database, read-only 여부가 쿼리 작성 중과 결과 화면에도 남아 있어야 합니다.

색상만으로 구분하면 tmux theme이나 접근성 문제도 있으니 텍스트가 같이 있어야 하고요.

**Interviewer:** SQL autocomplete나 query history는 얼마나 중요한가요?

**재민:** autocomplete는 있으면 좋지만 전환 이유는 아닙니다. history는 중요해요. 장애 중에 방금 실행한 쿼리를 수정하거나, 세션이 끊긴 다음 다시 실행하는 일이 많거든요.

다만 history에 개인정보나 민감한 값이 평문으로 남는 방식이면 꺼야 합니다. 저장 위치와 삭제 방법이 명확해야 해요.

**Interviewer:** datavase를 한 번 사용했다면 두 번째 사용을 결정하는 순간은 언제일까요?

**재민:** 첫 사용에서 tunnel 연결, 쿼리 실행, 복사가 한 번도 걸리지 않았는지가 중요해요. 특히 터미널 크기를 바꾸거나 tmux pane 안에서 열었을 때 화면이 깨지면 바로 mysql로 돌아갑니다.

장애 때 쓰는 도구는 편리함보다 예측 가능성이 먼저예요.

**Interviewer:** 다음 중 하나만 개선할 수 있다면 무엇을 고르겠습니까?

1. 더 강한 SQL autocomplete
2. EXPLAIN 시각화
3. 여러 query tab
4. datasource 가져오기와 SSH 연결 진단
5. 더 많은 export 형식

**재민:** 4번이요. 나머지는 DataGrip에서 하면 됩니다. 처음 접속하지 못하면 다른 기능은 평가할 기회도 없어요.

**Interviewer:** 개인적으로 만족하면 팀에 사용을 권하겠습니까?

**재민:** 링크는 공유할 수 있어요. 하지만 팀 표준으로 만들지는 바로 결정하지 않을 겁니다.

공통 도구가 되면 누군가는 설치 문제, config 형식 변경, macOS와 Linux 차이, 보안 검토를 책임져야 해요. 제가 혼자 쓰는 것과 팀에 추천하는 것 사이에 기준이 꽤 큽니다.

**Interviewer:** 팀 표준으로 제안할 조건은 무엇인가요?

**재민:** 최소 몇 달간 release가 안정적이고, 이전 버전 config가 깨지지 않고, 보안 이슈 대응 방법이 보여야 해요. CI로 설치 가능한 고정 버전과 checksum도 필요하고요.

그리고 팀원들이 mysql보다 실제로 빠르게 문제를 해결했다는 사례가 두세 번은 있어야 합니다.

**Interviewer:** 제품 설명으로 다음 중 어느 것이 가장 적절합니까?

1. A lightweight alternative to DataGrip
2. A safer MySQL client for the terminal
3. A reliable production-read workflow for MySQL
4. A modern terminal database IDE

**재민:** 3번이 제가 기대하는 사용 장면과 제일 가까워요. 2번은 read-only가 제품 전체를 책임지는 것처럼 들리고, 1번과 4번은 DataGrip 기능 목록과 비교하게 만듭니다.

다만 “reliable”이라고 쓰려면 실제로 증명해야죠. 개발자가 선언한다고 믿을 수 있는 표현은 아닙니다.

**Interviewer:** 지금 사용 중인 `mysql`을 datavase로 완전히 바꾸려면 무엇이 확인돼야 하나요?

**재민:** 완전히 바꿀 필요는 없다고 생각해요. datavase가 빠른 운영 조회의 기본값이 되고, 예상 밖의 상황에서 mysql이 fallback이면 충분합니다.

그 상태가 되려면 열 번 정도 사용했을 때 접속 실패나 화면 문제 없이 더 빠르다는 경험이 누적돼야 해요.

### 결정적 발언

> “설치 권한과 전환 의지는 다른 문제예요. 기존 workflow가 이미 80점이면 새 도구가 조금 더 편하다는 설명만으로는 부족합니다.”

> “운영 DB 안전은 계정 권한에서 보장해야 하고, 클라이언트 read-only는 안전벨트 정도로 설명해야 맞아요.”

> “장애 때 쓰는 도구는 편리함보다 예측 가능성이 먼저예요.”

### Interview 07 결과

이 페르소나는 설치 권한, SQL 숙련도, 터미널 친숙도가 모두 높지만 즉시 채택 가능성은 중간 이하이다. 자율성이 높다고 전환 비용이 낮아지는 것은 아니다. 숙련 사용자는 이미 shell script, mysql 옵션, query 작성 습관으로 불편을 상당 부분 제거했으며 새로운 도구가 추가하는 학습·업데이트·fallback 비용까지 함께 평가한다.

`read_only`는 긍정적인 사고 방지 장치지만 운영 안전의 주된 근거가 되지 못했다. DB 계정이 이미 SELECT-only인 조직에서는 차별성이 더 약해진다. 오히려 persistent environment identity, datasource 가져오기, SSH 연결 신뢰성, history 관리 방식이 시험 사용과 반복 사용에 더 큰 영향을 준다.

이 사용자의 전환은 설치 한 번이 아니라 다음 단계로 구분해야 한다.

1. 반복되는 mysql 출력 불편이나 동료의 사용 사례가 있어야 시험한다.
2. 별도의 복잡한 설정 없이 기존 접속 workflow를 옮길 수 있어야 첫 사용을 완료한다.
3. tmux, resize, reconnect, SSH tunnel 환경에서 여러 차례 실패하지 않아야 기본 도구가 된다.
4. config 안정성, 고정 버전 설치, checksum, 유지보수 신호가 확인돼야 팀에 추천한다.

따라서 개인 설치 수는 실제 retention이나 팀 채택을 과대평가할 수 있다. 시니어 사용자의 유효한 전환 지표는 설치보다 datasource 생성 완료, 두 번째 세션 실행, 반복 사용 횟수, mysql fallback 비율에 가깝다.

### 실제 사용자 검증 후보

- 개인 도구 설치 권한이 있는 시니어 개발자 중 최근 30일 내 `mysql` CLI를 사용한 사람을 모집한다.
- 마지막 운영 조회를 화면 공유로 재현하게 하고 환경 확인, tunnel 실행, 쿼리 작성, 결과 공유에 걸린 시간을 기록한다.
- DB 계정이 SELECT-only인 사용자와 쓰기 권한을 가진 사용자를 분리해 `read_only`의 실제 가치를 비교한다.
- 기존 datasource를 직접 등록하게 하여 문서 조회 횟수, 중단 지점, 접속 성공률을 측정한다.
- tmux pane resize, SSH 재연결, 장시간 idle 후 재실행을 포함한 반복 과제를 수행하게 한다.
