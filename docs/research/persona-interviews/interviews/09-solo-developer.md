## Interview 09 — 이도윤: 운영 DB를 가끔 확인하는 1인 개발자

> 합성 페르소나 시뮬레이션이며 실제 사용자 인터뷰나 수요의 증거가 아니다.

### 페르소나

- 32세, 1인 SaaS 개발·운영자, 개발 경력 7년
- 고객 40여 곳이 사용하는 소규모 예약 관리 서비스를 혼자 운영
- Spring Boot, Nuxt, MySQL 8, AWS Lightsail 기반의 단순한 인프라 사용
- 개발 환경에서는 DataGrip을 사용하고 production DB는 필요할 때 SSH tunnel을 열어 확인
- 고객 문의, 결제, 개발, 배포를 혼자 담당하므로 새로운 도구의 학습과 유지에 쓸 시간이 적음
- production DB 직접 조회는 월 1~3회 수준이며 장애가 없으면 한 달 이상 접속하지 않기도 함
- 오픈소스 CLI를 발견하면 설치해보는 편이지만, 반복 사용하지 않으면 빠르게 삭제하거나 잊음

### 인터뷰 목적

production DB 조회 빈도가 낮은 개인 개발자도 datavase를 설치하고 계속 사용할 수 있는지 검증한다. 단순 설치, 저장된 datasource, read-only, CSV가 초기 관심을 만들더라도 낮은 사용 빈도에서 설정과 조작법을 기억하고 재사용할 만큼 충분한 가치가 있는지 살펴본다.

### 인터뷰

**Interviewer:** 최근 production DB에 직접 접속했던 일을 처음부터 설명해주세요.

**도윤:** 지난주에 고객이 예약 완료 문자를 못 받았다고 연락했어요. 로그에서 reservation id를 찾고 DataGrip에서 SSH tunnel이 설정된 production datasource를 열었습니다. 예약 row와 메시지 발송 이력을 확인했는데 데이터는 정상이었고 외부 문자 API가 늦게 처리된 문제였어요.

**Interviewer:** production DB는 얼마나 자주 확인하나요?

**도윤:** 일정하지 않아요. 문제가 몰리면 일주일에 두세 번 볼 때도 있지만, 평소에는 한 달에 한두 번 정도예요. 두 달 가까이 직접 안 본 적도 있습니다.

**Interviewer:** 그때마다 DataGrip을 사용하나요?

**도윤:** 대부분 그렇습니다. 이미 개발 DB와 production DB가 등록돼 있고 tunnel 설정도 저장돼 있으니까요. 서버에 SSH로 들어가 있는 상태라면 `mysql`을 쓸 때도 있지만, 컬럼이 많으면 그냥 DataGrip을 켭니다.

**Interviewer:** mysql CLI를 사용할 때 불편했던 최근 사례가 있습니까?

**도윤:** 주문 테이블을 `select *`로 봤다가 줄이 다 깨진 적은 있어요. `\G`로 다시 실행해서 봤습니다. 불편하긴 했지만 명령 하나 더 친 정도라서 도구를 바꿔야겠다는 생각은 안 했어요.

**Interviewer:** 터미널에서 결과를 grid로 볼 수 있다면 도움이 될까요?

**도윤:** 보기에는 좋겠죠. 그런데 그 일이 한 달에 한 번이면 설치하고 설정하는 시간이 더 클 수도 있습니다. 이미 DataGrip이 해결하고 있으니까요.

**Interviewer:** datavase는 single binary이고 별도 runtime이나 driver가 필요하지 않습니다.

**도윤:** 설치 자체는 부담 없네요. Homebrew 한 줄이면 호기심으로 설치할 수는 있어요.

**Interviewer:** 그러면 실제 사용으로 이어질까요?

**도윤:** 설치와 사용은 다른 문제예요. 설치한 날 production datasource까지 바로 등록하면 한 번은 쓰겠죠. 그런데 다음 접속이 한 달 뒤라면 프로그램 이름이나 실행 방법부터 기억해야 할 수 있어요.

**Interviewer:** datasource를 한 번 저장하면 다음에는 `dv open production`으로 바로 열 수 있습니다.

**도윤:** 그건 괜찮습니다. 다만 SSH key 위치나 port 같은 설정을 다시 손볼 일이 없어야 해요. 한동안 안 쓰다가 실행했는데 설정 형식이 바뀌었거나 tunnel 오류가 나면 고치지 않고 DataGrip으로 돌아갈 것 같습니다.

**Interviewer:** production datasource에 `read_only: true`를 설정할 수 있습니다.

**도윤:** 혼자 운영하다 보니 실수로 데이터를 바꿔도 막아줄 사람이 없어서 의미는 있어요. production 연결이 눈에 띄고 write가 막히면 마음은 편하겠죠.

**Interviewer:** 실제로 production에서 잘못 write한 경험이 있습니까?

**도윤:** 큰 사고는 없어요. UPDATE 전에 transaction을 열거나 먼저 SELECT를 실행하는 습관이 있습니다. 예전에 개발 DB인 줄 알고 production에서 SELECT를 실행한 적은 있지만 데이터 변경은 아니었어요.

**Interviewer:** 그렇다면 read-only가 설치 이유가 될까요?

**도윤:** 단독으로는 아니요. 실제 사고 경험도 없고 접속 빈도도 낮으니까요. 이미 DB 계정을 read-only로 분리하는 게 더 확실하다고 생각합니다. datavase의 설정은 추가 안전장치 정도예요.

**Interviewer:** 고객 요청으로 데이터를 CSV로 전달할 일은 있나요?

**도윤:** 분기마다 한 번 정도 있습니다. 고객사의 예약 내역이나 정산 자료를 조건에 맞춰 보내달라는 요청이에요. DataGrip export를 쓰거나 작은 관리 화면에서 내려받습니다.

**Interviewer:** 결과를 바로 CSV로 저장할 수 있다면 어떻습니까?

**도윤:** 편하긴 하지만 빈도가 너무 낮아요. 그 기능 때문에 별도 프로그램을 계속 유지하지는 않을 것 같습니다. 저장 경로와 개인정보 컬럼을 매번 확인해야 해서 어차피 파일을 다시 열어보기도 하고요.

**Interviewer:** 새로운 도구를 계속 사용하게 만드는 것은 무엇인가요?

**도윤:** 자주 쓰거나, 기존 도구로 불가능한 일을 해결하거나, 다음에 쓸 때 생각할 필요가 없어야 합니다. datavase는 세 번째가 중요해 보여요. 실행했을 때 저장된 연결이 그대로 열리고 화면에서 어떻게 실행하는지 바로 보여야 합니다.

**Interviewer:** 단축키를 기억해야 한다면요?

**도윤:** 한 달에 한 번 쓰는 프로그램의 단축키는 못 외웁니다. 화면에 표시된 실행 버튼이나 키 안내만 사용하게 될 거예요. F5도 DataGrip에서는 익숙하지만 터미널 프로그램에서 같은지 기억 못 할 수 있습니다.

**Interviewer:** query history가 있으면 재사용에 도움이 될까요?

**도윤:** 조금은요. 다만 지난달에 실행한 SQL보다 고객 문의마다 다른 SQL을 만드는 경우가 많습니다. history가 있다고 사용 빈도가 늘지는 않을 것 같아요.

**Interviewer:** 시작할 때 마지막 datasource와 query를 복원하면 어떨까요?

**도윤:** 편할 수 있지만 production에서 지난 query가 자동 실행되거나 실행할 것처럼 보이면 불안합니다. 연결과 편집 내용은 복원해도 실행은 명시적으로 해야 해요. 그리고 지금 production인지 아주 분명해야 합니다.

**Interviewer:** README의 짧은 demo에서 read-only로 UPDATE가 거부되는 장면을 봤다면 설치하겠습니까?

**도윤:** GitHub를 둘러보다 발견했다면 설치할 가능성은 있습니다. 작은 Go CLI를 시험해보는 건 좋아하거든요. 하지만 그 관심이 다음 달 실제 고객 문의 때 datavase를 떠올린다는 뜻은 아닙니다.

**Interviewer:** 설치 후 첫 사용을 성공했다면 계속 남겨둘까요?

**도윤:** binary 하나라면 굳이 지우지는 않을 것 같아요. 그래도 설치돼 있다는 사실을 잊을 수 있습니다. 제 입장에서는 삭제되지 않는 것보다 다음 작업에서 다시 선택되는지가 retention이죠.

**Interviewer:** DataGrip보다 datavase를 선택할 장면은 무엇입니까?

**도윤:** 이미 서버에 SSH로 들어가 있고 짧게 두세 row만 확인하면 될 때요. 다만 그 장면이 자주 발생하지 않습니다. 노트북에서 시작하면 DataGrip을 그대로 쓸 가능성이 높아요.

**Interviewer:** mysql CLI 대신 datavase를 기본값으로 바꿀 의향이 있습니까?

**도윤:** 서버마다 설치돼 있고 설정 없이 바로 실행된다면 가능할 수 있어요. 그런데 제가 관리하는 서버가 몇 개 안 되고 mysql도 이미 있으니 별도 설치를 계속 유지할 유인이 약합니다.

**Interviewer:** 개인 개발자를 위한 기능을 추가한다면 무엇이 필요할까요?

**도윤:** 기능을 늘린다고 사용 빈도가 높아지지는 않을 겁니다. 오히려 설치 후 바로 연결되고, 몇 달 뒤에도 같은 방식으로 열리는 게 중요해요. 저를 잡으려고 기능을 많이 추가하는 건 맞지 않는 것 같습니다.

**Interviewer:** 유료라면 사용할까요?

**도윤:** 월 구독은 안 합니다. 사용 빈도와 맞지 않아요. 일회성 결제도 DataGrip을 이미 구독하고 있어서 어렵습니다. 무료 오픈소스라면 시험하고 남겨둘 수는 있어요.

**Interviewer:** 지금 상태에서 datavase를 누구에게 추천하시겠습니까?

**도윤:** production DB를 터미널에서 매주 확인하는 개발자라면 추천해볼 수 있어요. 저처럼 가끔 보는 사람은 “있으면 편한 도구”지만 굳이 습관을 바꿀 정도는 아닙니다.

### 결정적 발언

> “설치한 날 한 번 쓰는 것과 한 달 뒤 고객 문의 때 다시 떠올리는 것은 다른 문제예요.”

> “한 달에 한 번 쓰는 프로그램의 단축키는 못 외웁니다.”

> “삭제되지 않는 것보다 다음 작업에서 다시 선택되는지가 retention이죠.”

### Interview 09 결과

낮은 빈도로 production DB를 확인하는 1인 개발자는 datavase를 쉽게 설치할 수 있지만, 반복 사용으로 이어질 가능성은 낮았다. single binary와 짧은 demo는 시험 설치를 유도하고, read-only와 저장된 datasource는 첫 사용의 부담을 줄인다. 그러나 기존 DataGrip 설정이 이미 존재하고 mysql CLI의 불편을 견뎌야 하는 횟수도 적어서 전환 압력이 약하다.

| 단계 | 반응 | 주요 조건 |
|---|---|---|
| 발견 | 관심 가능 | 짧은 demo와 명확한 production-read 메시지 |
| 설치 | 비교적 쉬움 | Homebrew 한 줄, 별도 runtime 없음 |
| 첫 사용 | 조건부 가능 | SSH datasource 설정이 즉시 성공해야 함 |
| 두 번째 사용 | 불확실 | 프로그램 이름과 조작법을 다시 떠올려야 함 |
| 장기 retention | 낮음 | 월 1~3회의 낮은 문제 빈도와 DataGrip 대체재 존재 |
| 추천 | 제한적 가능 | 더 자주 terminal DB workflow를 수행하는 동료 대상 |

이 페르소나에게 가장 큰 경쟁자는 다른 terminal client가 아니라 **이미 설정된 DataGrip과 낮은 문제 빈도**다. read-only는 정서적 안정감을 주지만 실제 write 사고 경험이 없고 DB 계정 권한이라는 더 강한 대안이 있어 핵심 전환 이유가 되지 못했다. CSV도 실제 업무 가치는 있으나 분기 단위 사용으로 retention을 만들기 어렵다.

따라서 개인 개발자라는 직업·회사 규모만으로 ICP를 정의해서는 안 된다. 같은 1인 개발자라도 terminal production 조회가 주 단위로 반복되는지, 기존 GUI 연결이 불편한지, SSH 내부에서 작업을 시작하는지가 적합도를 더 잘 구분한다.

### 실제 사용자 검증 후보

1. 1인 개발자가 최근 90일 동안 production DB에 직접 접속한 실제 횟수와 시작 위치를 확인한다.
2. 시험 설치 후 30일 이내 두 번째 실행이 발생하는지 측정하고, 재실행 계기를 인터뷰한다.
3. README 방문, 설치, datasource 생성, 첫 query, 30일 재사용을 별도 전환 단계로 측정한다.
4. 재사용하지 않은 사용자가 datavase를 잊었는지, 설정 실패를 겪었는지, 기존 GUI로 복귀했는지 구분한다.
5. 한 달 이상 사용하지 않은 뒤에도 화면 안내만으로 query 실행·CSV 저장·datasource 변경이 가능한지 관찰한다.
6. read-only가 실제 과거 사고나 불안에서 나온 필요인지, 설명을 들은 뒤 생긴 긍정 반응인지 구분한다.
7. 개인 개발자군을 직함이 아니라 월간 terminal DB workflow 횟수와 기존 GUI 접근 비용으로 세분화한다.
8. 설치 유지 여부가 아니라 두 번째와 세 번째 실제 업무 선택을 retention 지표로 사용한다.
