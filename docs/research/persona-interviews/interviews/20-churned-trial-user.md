## Interview 20 — 이준호: 데모를 보고 설치했지만 mysql로 돌아간 이탈 사용자

> 합성 페르소나 시뮬레이션이며 실제 사용자 인터뷰나 수요의 증거가 아니다.

### 페르소나

- 35세, Backend Engineer, 경력 9년
- 개발자 24명 규모의 커머스 스타트업에서 Java·Spring Boot와 MySQL 8 운영을 담당
- macOS에서 개발하며 production 접근은 VPN 연결 후 bastion에 SSH하는 방식
- 복잡한 개발·분석 작업은 DataGrip, 장애 중 짧은 조회는 bastion의 `mysql` CLI 사용
- GitHub에서 read-only 거부 장면이 포함된 datavase 데모를 보고 Homebrew로 직접 설치
- production과 staging datasource를 설정해 사흘 동안 네 차례 사용한 뒤 기존 도구로 복귀
- 새로운 도구에 적대적이지 않지만, 장애 대응 도구는 첫 실패 이후 다시 기회를 거의 주지 않음
- 기능 선호가 아니라 실제 설치부터 이탈까지의 행동을 회고하도록 구성된 페르소나

### 인터뷰 목적

README와 데모가 설치를 유도한 뒤 실제 사용이 반복되지 않는 activation·retention 실패를 추적한다. 설치 수를 관심의 증거로 과대평가하지 않고, 사용자가 어느 단계에서 기대와 현실의 차이를 경험했는지, mysql 또는 DataGrip으로 돌아간 정확한 순간과 재시도 조건이 무엇인지 확인한다.

### 인터뷰

**Interviewer:** datavase를 처음 알게 된 순간부터 설명해주세요.

**준호:** GitHub에서 terminal database client를 찾다가 README를 봤습니다. 결과가 grid로 나오고 마지막에 UPDATE가 read-only라서 거부되는 짧은 데모가 있었어요. 당시 운영 주문 데이터를 확인할 일이 많아서 `ssh → mysql` 대신 쓸 수 있겠다고 생각했습니다. Homebrew 명령이 한 줄이라 바로 설치했어요.

**Interviewer:** 어떤 기능이 설치를 결정하게 했습니까?

**준호:** read-only가 가장 컸고, 그다음이 결과 화면과 CSV였습니다. 운영 접속에서 실수 방지가 된다는 설명이 구체적이었어요. DataGrip 대체라고 했다면 설치하지 않았을 텐데 mysql 대신이라는 설명은 납득됐습니다.

**Interviewer:** 설치 직후 무엇을 했나요?

**준호:** 먼저 로컬 Docker MySQL을 연결했습니다. 샘플 쿼리를 실행하고 방향키로 결과를 움직여봤어요. 그 단계는 금방 됐고 화면도 괜찮았습니다. 그다음 staging datasource를 만들었는데 config 항목 이름을 README와 예제 사이에서 몇 번 오갔습니다.

**Interviewer:** 첫 사용을 성공했다고 느낀 순간이 있었습니까?

**준호:** 로컬에서 SELECT 결과를 보고 셀 하나를 복사했을 때는 성공했다고 생각했어요. 하지만 그건 제품의 실제 목적을 검증한 순간은 아니었습니다. production 경로에서 기존 mysql보다 빨라져야 했는데 거기까지는 아직이었죠.

**Interviewer:** staging에서는 어땠습니까?

**준호:** bastion을 통해 연결하고 주문 상태를 조회했습니다. 첫 연결은 됐어요. 그런데 터미널 폭이 좁아서 컬럼을 확인하려고 이동했고, 키 조작을 잠깐 찾았습니다. 그래도 mysql의 깨진 표보다는 보기 좋았습니다.

**Interviewer:** 그날 다시 사용했나요?

**준호:** 한 번 더 사용했습니다. CS 요청으로 결과를 CSV로 저장했는데 저장 위치를 바로 확신하지 못했어요. 파일은 만들어졌지만 어디에 저장됐는지 확인하려고 shell로 돌아갔고, 컬럼 값에 줄바꿈이 있어서 열어본 뒤 원본과 맞는지도 재확인했습니다. 편리하긴 했지만 아직 신뢰해서 바로 전달하지는 못했습니다.

**Interviewer:** 가장 처음 생긴 불신은 무엇이었습니까?

**준호:** 에러라기보다 제가 현재 어느 datasource에 있는지 순간적으로 헷갈린 일이었습니다. staging을 보고 있다고 생각했는데 production 이름도 비슷하게 등록해뒀거든요. 헤더를 다시 보고 확인했습니다. 이후에는 쿼리 실행 전에 프롬프트와 `SELECT DATABASE()`를 보는 기존 mysql 습관이 더 안전하게 느껴졌어요.

**Interviewer:** read-only 표시가 그 불안을 해결하지 않았나요?

**준호:** production datasource가 read-only라는 건 보였지만, 그 표시가 실제 세션에도 적용됐는지 눈으로 확인하고 싶었습니다. 데모에서는 UPDATE가 막혔지만 제 연결에서 직접 시험하려니 production에 write 문을 입력하는 행동 자체가 꺼려졌어요. 결국 `@@transaction_read_only`를 조회했습니다. 제품이 설정한 상태와 서버가 보고하는 상태를 함께 보여주면 덜 불안했을 것 같습니다.

**Interviewer:** 사용을 중단한 정확한 사건은 무엇입니까?

**준호:** 셋째 날 장애 대응 중이었습니다. bastion 연결이 잠깐 끊겼다가 돌아왔고 기존 화면에서 쿼리를 다시 실행했는데 connection 관련 오류가 났습니다. 재연결 방법을 찾는 몇 초 동안 옆 터미널에서 평소 쓰던 SSH 명령과 mysql을 실행했어요. mysql로 필요한 값을 먼저 찾은 뒤 datavase로 돌아갈 이유가 없어 그대로 닫았습니다.

**Interviewer:** 몇 초가 그렇게 결정적이었나요?

**준호:** 평소라면 문서를 볼 수 있지만 장애 중에는 아니죠. 제가 원하는 건 예쁜 오류보다 연결이 끊겼다는 사실, 재연결했는지, 새 세션에도 read-only가 다시 적용됐는지가 명확한 것입니다. 기존 명령은 손에 익어 있어서 생각하지 않고 실행할 수 있었어요.

**Interviewer:** 자동 reconnect가 있었다면 계속 사용했을까요?

**준호:** 무조건 자동이면 그것도 불안합니다. 쿼리를 재실행했는지, transaction이나 session state가 어떻게 됐는지 모를 수 있으니까요. 연결이 끊겼다고 명확히 알리고, 새 세션을 여는 동작과 적용된 database·read-only 상태를 보여주는 편이 낫습니다.

**Interviewer:** 그 이후 datavase를 다시 열어본 적이 있습니까?

**준호:** 다음 날 한 번 열었습니다. 재연결 동작을 확인하려고 staging에서 시험했는데, 그때는 긴급하지 않았고 정상적으로 썼어요. 그래도 실제 업무에서는 다시 mysql과 DataGrip으로 돌아갔습니다. 성공 한 번이 장애 때의 실패 기억을 지우지는 못했습니다.

**Interviewer:** 삭제하지는 않았나요?

**준호:** 아직 설치는 되어 있을 겁니다. 하지만 shell history에서 실행하지 않으니 사실상 이탈한 상태입니다. 설치 여부로 활성 사용자를 판단하면 저를 잘못 셀 것 같아요.

**Interviewer:** 두 번째 주에 datavase 대신 mysql을 선택한 첫 상황을 설명해주세요.

**준호:** 로그에서 customer ID를 보고 production row 하나를 확인해야 했습니다. datavase도 할 수 있었지만 새 도구를 열고 datasource를 고르는 것보다 복사해둔 mysql 접속 명령을 실행했습니다. 조회는 30초 만에 끝났어요. 작은 작업에서는 기존 습관의 비용이 거의 없었습니다.

**Interviewer:** 그러면 제품의 성능 문제가 아니라 습관 문제인가요?

**준호:** 둘을 분리하기 어렵습니다. 새 도구는 기존 습관보다 훨씬 확실히 좋아야 합니다. 저에게는 접속 명령이 이미 shell history와 script에 있고, mysql의 불편한 출력도 필요한 컬럼만 선택하면 피할 수 있어요. datavase의 이점이 학습과 불확실성을 상쇄하지 못했습니다.

**Interviewer:** DataGrip으로 돌아간 작업은 무엇이었습니까?

**준호:** 주문과 결제 테이블을 여러 번 조회하고 조건을 수정하던 분석입니다. 쿼리 탭, history, schema 탐색을 계속 쓰게 돼서 DataGrip을 열었습니다. datavase가 그 기능들을 모두 가져야 한다고 생각하지는 않아요. 그런 작업은 애초에 제품이 이길 대상이 아닙니다.

**Interviewer:** mysql 대신 쓸 좁은 작업에서는 어떤 가치가 남았습니까?

**준호:** 컬럼이 많은 결과 확인과 한두 행 복사, read-only datasource는 여전히 좋습니다. 하지만 제가 일주일에 그 문제를 겪는 횟수가 생각보다 적었어요. README를 볼 때는 자주 쓸 것 같았는데 실제로 기록해보면 대부분 필요한 컬럼만 조회했고 CSV도 월 한두 번이었습니다.

**Interviewer:** CSV export가 retention을 만들지 못한 이유는 무엇인가요?

**준호:** 빈도가 낮았고, 파일을 외부에 전달하기 전 값과 quoting을 검증해야 했기 때문입니다. DataGrip export는 팀에서 이미 익숙하고 옵션도 알고 있습니다. 새 exporter는 NULL, 줄바꿈, timezone, 큰 숫자가 어떻게 나오는지 확인하기 전에는 바로 신뢰하기 어렵습니다.

**Interviewer:** 온보딩에서 무엇이 부족했습니까?

**준호:** 기능 설명은 충분했습니다. 부족했던 건 “첫 production 사용 전에 무엇을 검증해야 하는가”였습니다. 연결 끊김, read-only 실제 상태, CSV 표현, secret 저장 방식을 staging에서 확인하는 짧은 체크가 있었다면 기대를 현실적으로 맞췄을 것 같아요.

**Interviewer:** 제품이 첫 실행 때 그 체크를 강제해야 합니까?

**준호:** 강제하면 귀찮을 수 있습니다. production datasource를 처음 열 때 선택적으로 health check를 실행하고 결과를 보여주는 정도가 좋겠어요. 다만 이것도 제 경험에서 나온 가설이지 모든 사람에게 필요한 기능이라고 단정할 수는 없습니다.

**Interviewer:** 알림이나 사용 팁을 보내면 다시 돌아올까요?

**준호:** 일반적인 팁은 아닐 것 같습니다. 제가 이탈한 원인과 연결된 개선, 예를 들면 reconnect 후 세션 상태를 검증해 보여준다는 릴리스가 있어야 다시 시험합니다. “새 기능이 추가됐다”보다 “당신이 실패한 경로가 이제 재현 테스트된다”가 더 설득력 있어요.

**Interviewer:** issue를 직접 작성하지 않은 이유는 무엇입니까?

**준호:** 장애가 끝난 뒤에는 본업으로 돌아갔고, 정확한 재현 방법도 정리하지 않았습니다. 무료 도구를 며칠 쓴 입장에서 report할 의무도 느끼지 않았어요. 조용히 이탈하는 사용자가 issue 작성자보다 훨씬 많을 것 같습니다.

**Interviewer:** 앱 안에서 실패 직후 feedback을 요청했다면 응답했을까요?

**준호:** 쿼리나 접속 정보가 전송되지 않는다는 게 분명하고 한두 선택으로 끝난다면 가능했을 겁니다. 장애 중에는 작성하지 않고 종료 후 선택할 수 있어야 해요. 자동으로 SQL이나 host를 수집하면 사용하지 않을 겁니다.

**Interviewer:** 어떤 측정이 activation을 가장 잘 나타낼까요?

**준호:** 설치나 첫 로컬 연결보다, 실제로 저장한 datasource를 다른 날 다시 열어 SELECT를 성공한 횟수라고 봅니다. 가능하면 production인지 수집하지 말고 사용자가 만든 datasource의 재방문 정도만 로컬 또는 명시적 opt-in으로 측정해야겠죠.

**Interviewer:** retention은 무엇으로 판단해야 합니까?

**준호:** 설치 7일 뒤에도 실행 파일이 있다는 것으로는 부족합니다. 서로 다른 날에 반복 실행했고, 연결 실패 뒤에도 다시 성공했는지가 중요합니다. 다만 데이터베이스 도구는 사용 빈도가 낮을 수 있으니 주간 활성 하나로 판단하면 실제 사용자를 놓칠 수도 있어요.

**Interviewer:** 다시 사용해볼 최소 조건 세 가지를 꼽는다면요?

**준호:** 첫째, 연결 단절과 reconnect 흐름이 명확할 것. 둘째, 새 세션의 datasource·database·read-only 실제 상태가 눈에 보일 것. 셋째, 제가 쓰는 MySQL 값들이 CSV와 clipboard에서 손실되지 않는다는 회귀 테스트가 공개될 것. 기능 수보다 그 세 가지가 중요합니다.

**Interviewer:** query history나 여러 탭은 필요하지 않습니까?

**준호:** 있으면 좋지만 그것 때문에 돌아오지는 않습니다. 그런 기능을 늘리면 DataGrip과 비교하게 됩니다. 제가 이탈한 이유는 작은 제품이라서가 아니라, 작은 핵심 경로를 아직 신뢰하지 못했기 때문입니다.

**Interviewer:** 현재 제품을 동료에게 추천하겠습니까?

**준호:** 지금은 데모 링크 정도만 공유할 수 있고 운영 도구로 추천하지는 않겠습니다. staging에서 연결 단절을 반복해도 상태가 예측 가능하고, 몇 주 동안 제가 먼저 mysql을 선택하지 않게 되면 그때 추천할 수 있습니다.

**Interviewer:** README가 설치 전 기대를 잘못 만들었나요?

**준호:** 거짓말을 했다고 생각하지는 않습니다. 다만 데모는 모든 것이 정상인 23초만 보여줬고, 실제 retention은 네트워크가 끊긴 다음 23초에 결정됐습니다. happy path 다음에 복구 장면까지 보여주면 저 같은 사용자는 더 정확히 판단할 수 있을 것 같아요.

**Interviewer:** 마지막으로, 왜 떠났는지 한 문장으로 말해주세요.

**준호:** 첫 쿼리는 mysql보다 보기 좋았지만, 첫 연결 실패에서는 mysql보다 확실하지 않았기 때문입니다.

### 결정적 발언

> “설치되어 있다는 것과 다시 선택한다는 것은 전혀 다른 상태입니다.”

> “데모의 happy path가 설치를 만들었지만, 네트워크가 끊긴 다음 23초가 이탈을 만들었습니다.”

> “작은 제품이라 떠난 게 아니라 작은 핵심 경로를 아직 신뢰하지 못해서 떠났습니다.”

> “첫 쿼리는 mysql보다 보기 좋았지만, 첫 연결 실패에서는 mysql보다 확실하지 않았습니다.”

### Interview 20 결과

이 페르소나는 positioning과 배포 경로가 실제 설치까지는 작동한 사례다. `ssh → mysql` 대체 메시지, read-only 거부 데모, 단일 설치 명령은 관심을 행동으로 전환했다. 그러나 로컬 SELECT 성공을 activation으로 간주하면 이후 이탈을 설명할 수 없다. 이 사용자에게 의미 있는 activation은 실제 bastion 경로의 저장된 datasource를 다른 날 다시 열고, 연결 단절 후에도 안전하게 복구해 업무를 끝내는 것이었다.

| 단계 | 사용자 행동 | 작동한 요소 | 이탈 위험 |
|---|---|---|---|
| 발견 | GitHub README와 데모 확인 | mysql 대체라는 좁은 설명 | 정상 경로만 보여 기대가 과도해짐 |
| 설치 | Homebrew로 즉시 설치 | 단일 명령, 낮은 시험 비용 | 설치를 수요나 retention으로 오인 |
| 첫 실행 | 로컬 MySQL에서 SELECT·copy | grid와 기본 조작 | 실제 접근 경로를 검증하지 않음 |
| 첫 업무 | bastion을 거쳐 staging 조회 | 읽기 좋은 결과 화면 | datasource·database context 재확인 필요 |
| 가치 시험 | CSV 저장, read-only 상태 조회 | export와 사고 방지 기대 | 값 정확성과 실제 session 상태를 별도 검증 |
| 결정적 실패 | 연결 단절 뒤 재실행 | 없음 | reconnect·새 session 상태가 불명확 |
| fallback | 옆 터미널에서 SSH와 mysql 실행 | 기존 muscle memory와 예측 가능성 | 업무 완료 후 제품으로 돌아올 이유가 사라짐 |
| 이탈 | 설치는 유지하되 실행 중단 | 낮은 삭제 마찰 | installed base가 활성 사용자처럼 보임 |
| 회복 가능성 | 원인과 직접 관련된 개선을 기다림 | 좁고 검증 가능한 reliability 약속 | 일반 기능 추가나 팁은 복귀 동기가 아님 |

가장 중요한 관찰은 acquisition과 retention의 가치 기준이 다르다는 것이다. read-only와 grid는 README에서 제품 차이를 빠르게 전달하지만, 반복 사용은 reconnect, 현재 context, 값 보존처럼 눈에 덜 띄는 신뢰 조건에 좌우된다. 따라서 데모 조회나 설치 수가 증가해도 저장된 datasource의 재방문과 두 번째·열 번째 성공이 확인되지 않으면 product fit의 증거로 해석해서는 안 된다.

또한 이탈을 더 많은 기능의 요구로 해석하지 않아야 한다. 이 사용자는 multiple tabs나 DataGrip 수준의 탐색 기능이 없어서 떠난 것이 아니다. 장애 중 연결이 끊겼을 때 새 세션의 상태를 예측할 수 없었고, 기존 mysql workflow가 즉시 성공했기 때문에 돌아갔다. 복구 우선순위는 기능 면적 확대가 아니라 핵심 경로의 관찰 가능성과 재현 가능한 신뢰성이다.

회복 전략은 모든 이탈 사용자에게 알림을 보내는 것이 아니라 실패 유형을 안전하게 분류하고, 해당 경로가 개선됐다는 구체적인 근거를 제공하는 것이다. SQL, hostname, credential 같은 민감 정보를 수집하지 않는 opt-in feedback과 reconnect 회귀 테스트가 후보가 될 수 있다. 다만 이는 합성 페르소나에서 나온 가설이므로 실제 이탈 사용자 인터뷰, 익명화된 사용 신호 또는 support report로 확인하기 전에는 구현 우선순위의 근거가 될 수 없다.

초기 ICP에는 높은 표면 적합도를 보였지만 retention 실패 사례다. 이 사례가 실제 사용자에게 반복된다면 datavase의 가장 큰 병목은 설치 전환이 아니라 first failure recovery일 가능성이 있다.

### 검증 후보

다음 항목은 이 페르소나의 가정을 실제 사용자 인터뷰와 제품 테스트로 검증하기 위한 후보이다.

1. README 방문, 데모 재생, 설치, 첫 연결, 첫 SELECT 중 어느 이벤트가 실제 두 번째 사용과 가장 강하게 연결되는지
2. 로컬 database의 첫 성공과 bastion·VPN을 포함한 실제 datasource 성공을 activation에서 분리해야 하는지
3. 설치 후 1일·7일·30일 내 서로 다른 날에 같은 datasource를 다시 여는 비율
4. 첫 connection error 뒤 세션 내 재시도, 성공, 종료 및 이후 재방문 비율
5. 사용자가 reconnect 후 datasource, database, server endpoint, session read-only를 정확히 인식하는지
6. 명시적 reconnect와 자동 reconnect 중 장애 대응에서 더 예측 가능하고 안전하다고 느끼는 방식
7. reconnect 시 새 session에 read-only와 기타 필수 설정이 재적용되고 UI 상태와 일치하는지
8. NULL, multiline text, timezone, Unicode, binary, decimal, 큰 정수가 clipboard와 CSV에서 손실 없이 보존되는지
9. CSV를 생성한 사용자가 결과를 실제로 신뢰하기 전에 수행하는 수동 검증과 소요 시간
10. mysql로 fallback한 정확한 순간, 명령, 완료 시간 및 datavase로 돌아오지 않은 이유
11. 삭제하지 않았지만 30일 이상 실행하지 않은 설치를 활성 사용자와 구분할 수 있는 privacy-preserving 측정 방식
12. connection error 직후 SQL·host·credential을 수집하지 않는 opt-in feedback의 응답률과 신뢰 영향
13. 일반적인 release announcement와 실패 경로별 구체적인 recovery announcement의 재활성화율 차이
14. reconnect·session-state 회귀 테스트 공개가 query tabs 같은 신규 기능보다 재시험 의향에 더 큰 영향을 주는지
15. happy path 데모와 연결 단절·안전 복구를 포함한 데모가 설치율과 기대 정확성에 미치는 차이
16. 첫 10회 사용 동안 datavase와 mysql/DataGrip 선택을 일지로 기록했을 때 실제 작업별 선택 기준
